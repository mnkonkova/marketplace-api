# Телеграм-боты «Сотки»

Два бота: **креаторский** (исполнителю) и **клиентский** (заказчику).
Третьего, менеджерского, нет и не будет — всё, что адресовано
менеджеру, уходит в общий чат менеджеров через CRM-вебхук API
(`N8N_WEBHOOK_URL`). Решение владельца от 25 сентября: второй канал
означал бы две очереди доставки, два места привязки и вопрос «куда
смотреть» на каждом дежурстве.

Сервис отдельный, потому что ходить в `api.telegram.org` и принимать
вебхук Telegram должен кто-то, до кого Telegram достучится, — а до
нашего VDS он ходить не обязан.

## Что он делает и чего не делает

Делает:

- принимает апдейты Telegram: `/start <код>` (привязка), блокировку
  бота, обычные сообщения;
- принимает уведомления от нашего API и рассылает их **адресатам,
  которых API уже посчитал**.

Не делает **намеренно**:

- не хранит состояние. Привязки, дневной потолок в 30 сообщений и
  «кого касается это событие» живут в API. Своя копия любого из этих
  правил — это два ответа на один вопрос и однажды два сообщения
  одному человеку;
- не ведёт переписку. Работа живёт в кабинете, и делать вид, что
  здесь можно что-то решить, нечестно;
- не пишет в лог ни токенов, ни секретов, ни сырого `init_data`.

## Переменные окружения

| Имя | Зачем |
|---|---|
| `TELEGRAM_CREATOR_BOT_TOKEN` | токен креаторского бота. Можно оставить пустым — тогда он просто не отвечает, а сервис поднимается |
| `TELEGRAM_CLIENT_BOT_TOKEN` | токен клиентского бота |
| `TELEGRAM_WEBHOOK_SECRET` | секрет в пути вебхука. Telegram шлёт апдейты без авторизации, и это единственное, что отличает его от любого, кто знает адрес |
| `API_BASE_URL` | адрес нашего API, например `https://api.sotka.io` |
| `BOT_SHARED_SECRET` | общий секрет группы `/api/v1/bot/*`. Тот же, что в `.env.prod` API |
| `BOT_WEBHOOK_SECRET` | ключ, которым API подписывает тело уведомления (`X-Signature`). Пусто — подпись не проверяется, и сервис об этом предупреждает при старте |
| `BOT_WEBHOOK_TOKEN` | bearer тех же уведомлений, если задан на стороне API |
| `APP_BASE_URL` | адрес кабинета: ссылки в сообщениях ведут туда, где человек сделает то, о чём его просят |
| `PORT` | Railway подставляет сам |

Те же токены прописываются и в `.env.prod` API (`TELEGRAM_*_BOT_TOKEN`):
подпись `initData` мини-аппа — чистая криптография над токеном, и
делать её здесь значит уронить вход в мини-апп вместе с этим сервисом.

## Выкатка

```bash
# Railway: новый проект → Deploy from repo → корень deploy/telegram-bot
# Переменные — из таблицы выше.

# После первого деплоя прописать вебхуки (адрес содержит секрет,
# поэтому в лог он не печатается):
PUBLIC_URL=https://<ваш-сервис>.up.railway.app npm run set-webhook
```

Проверка живости: `GET /health` отвечает `{"ok":true,"bots":[...]}`.

## Контракт с API

**Мы → бот.** `POST /notify`, тело — обычный payload outbox плюс два
поля:

```json
{
  "event_id": "12345",
  "event_type": "project.publication_due_today",
  "aggregate": "project",
  "aggregate_id": "…",
  "app_base_url": "https://sotka.io",
  "data": { "...": "payload события" },
  "bot": "creator",
  "recipients": [{ "user_id": "…", "tg_chat_id": 482512345 }]
}
```

Коды ответа читает outbox API, и они значат ровно это:

| Ответ | Что делает outbox |
|---|---|
| `2xx` | принято |
| `408`, `429`, `5xx` | повтор с backoff |
| любой другой `4xx` | в DLQ, повторов нет |

Поэтому «бот не настроен» и «неизвестный тип события» — это `200`, а
не `500`: нормальная ситуация, превращённая в пятисотку, стоит десяти
ретраев. Дедупликация по `event_id` — на нашей стороне: API повторяет
при любой ошибке, и без памяти человек получил бы дубль.

**Бот → API** (`Authorization: Bearer $BOT_SHARED_SECRET`):

- `POST /api/v1/bot/link` — `/start` с кодом;
- `GET /api/v1/bot/users/by-telegram/{tg_user_id}?bot=` — «кто это»;
  `404` значит «не привязан», и это нормальное состояние;
- `POST /api/v1/bot/blocked` — человек заблокировал бота.
